## Context

See proposal.md - Why. This is a provider-agnostic capability set: a checkout-session creation surface, a webhook/notification handler, and a config module. The concrete provider adapter (Stripe, PayPal, Paddle, Lemon Squeezy, etc.) is explicitly deferred and not designed here.

## Goals / Non-Goals

**Goals:**
- Make the checkout/webhook/grant logic provider-swappable via one config value, with zero provider-specific branching outside the adapter layer.
- Make webhook processing safe to receive duplicate "succeeded" deliveries without double-granting or double-logging.
- Keep the client-side redirect from ever being trusted as proof of payment.

**Non-Goals:**
- Choosing a provider or writing its concrete adapter.
- Pricing/bundle strategy.
- Download-compilation logic (the frontend's export capability consumes the resulting flag; not designed here).

## Decisions

- **Provider abstraction boundary is "common across major providers", not a full plugin interface**: this proposal describes behavior in terms of (a) hosted/embedded checkout, (b) server-to-server notification, (c) signed/verifiable payload — the smallest shared surface across Stripe/PayPal/Paddle/Lemon Squeezy. Alternative considered: designing a full adapter interface now — rejected as premature since no provider is chosen yet; over-designing the interface before a second real provider exists risks guessing wrong.
- **Idempotency key is the provider transaction/session id**, not a synthetic one — every major provider's webhook payload includes a stable transaction or session identifier, so deduping on it needs no extra state generated by this app.
- **`user_id` travels only through checkout-time metadata**, never re-derived from webhook payload email or customer fields, closing off a class of account-confusion bugs where a payment made under one email could otherwise grant access to the wrong account.
- **Processing state is a distinct third state** (not just true/false) between "unlocked" and "not started" — the UI needs to represent "redirected back, awaiting server confirmation" as its own state so it isn't confused with "purchase never attempted."

## Risks / Trade-offs

- [Risk] A future provider's verification mechanism might not fit the "signature/verification mechanism" abstraction cleanly (e.g. a provider requiring a callback API call instead of a signed payload) → Mitigation: the config point already isolates verification method per provider; this is exactly the kind of provider-specific detail meant to live in the adapter, not in the specs here.
- [Risk] Deduping solely on provider transaction/session id could under-dedupe if a provider reuses ids across environments (test/live) → Mitigation: the transaction log should key on (provider name, transaction/session id) together, not id alone — noted for the implementer of `transaction-logging`.
